# Приём STT/TTS с приоритетами

Общий Python-модуль подключается к существующим GigaAM/VoxCPM HTTP-приложениям при запуске `python -m speech_receiver.main --config /app/config/prod.yaml`. Отдельного gateway-контейнера нет. Прямой `uvicorn api:app` предназначен только для тестов моделей: в нём нет авторизации и приоритетной очереди, его нельзя публиковать клиентам.

## Контракт

- `POST /transcribe`: существующий multipart `file`, query `model`/`word_timestamps`.
- `POST /synthesize`: существующий JSON VoxCPM.
- `Authorization: Bearer TOKEN` обязателен. `clients` сопоставляет секрет с клиентом и `high`/`normal`; входному `priority` не доверяем.
- `Idempotency-Key` — до 128 печатных ASCII-символов, без пробелов. Ключ изолирован клиентом. Без ключа создаётся новая задача. Повтор с иными данными — 409. Для STT случайная multipart boundary не меняет идентичность.
- Ответ — существующий JSON/WAV; ошибка приёма — JSON `{"error":"safe_category"}`. 401 — авторизация, 413/415/422 — вход, 429 — отдельный лимит приоритета, 503 — недоступность/квота/истечение ожидания, 504 — истечение ожидания уже выполняющегося вычисления.
- `X-Voice-Execution-State`: `not-started`, `finished`, `uncertain`. Последнее запрещает считать вычисление остановленным. Подтверждённое состояние worker проверяется до чтения тела и сохраняется при обрыве чтения, превышении max_result_bytes и отказе сохранения результата из-за квоты: ошибка приёмника не превращает `finished`/`not-started` в `uncertain` и не удерживает завершённый слот. После разрыва соединения без ответа исход тоже неопределён.
- `/health/ready`: восстановление и подтверждённое состояние очереди; не проверка качества моделей. `/metrics` объединяет прежние модельные метрики с `receiver_*`.

HTTP-запрос ждёт результат; публичного API фоновых заданий нет. При отключении последнего ожидающего клиента queued-задача отменяется. Running-задача продолжает занимать слот до фактического завершения. Таймаут HTTP не останавливает поток инференса.

## Хранение и восстановление

Каждая операция имеет свой однопартиционный compacted topic с `retention.ms=-1`. Redpanda хранит идентификатор, приоритет, безопасные поля состояния и ссылки на файлы. Вход/результат — на постоянном volume: временный файл, fsync, rename, fsync каталога. Токены и тело запроса в Kafka не записываются. Квота `max_payload_bytes` общая для входов и результатов. Запись, fsync, чтение, удаление и проверка файлов выполняются в выделенном пуле с двумя потоками, с лимитом двух одновременно переданных операций. Общий lock состояния не удерживается во время файлового I/O: один медленный файл не задерживает допуск high и таймауты других задач. До записи резервируются очередь и дисковая квота; параллельные запросы с одним ключом разделяют admission и файл. Квота защищена короткой блокировкой арифметики без файловых операций. Чтение результата закрепляет запись от retention до завершения I/O; удаление после durable-перехода выполняется отдельно. Отмена ждёт завершения начатой файловой операции.

Переходы queued/running/конечное состояние записываются с подтверждённой Kafka-транзакцией. Стабильный transactional.id на топик ограждает прежнего владельца от новых записей; volume дополнительно блокируется flock. Replay читает только committed записи до барьера восстановления. Неопределённая запись останавливает допуск и завершает сервер; Compose перезапускает процесс. Ошибки журнала, файлов и worker логируются структурированным событием `receiver_error` с `operation`, `stage` и `error_type` (для системных файловых ошибок также `errno`); сообщения исключений, traceback, токены и содержимое запросов не записываются.

После перезапуска queued-задачи отменяются: прежние HTTP-владельцы потеряны. Running-задачи становятся failed с удержанным слотом, без повторной генерации. Успешный результат доступен повторным запросом с тем же ключом до `retention`. Завершённые записи удаляются tombstone-записью, затем удаляются файлы. Осиротевшие файлы удаляются при восстановлении.

**Один активный координатор на операцию.** Нельзя увеличивать Uvicorn workers или поднимать независимые coordinator-реплики для тех же моделей. Топик, volume и стабильные instance IDs образуют одну очередь. При переносе нужен тот же volume; отсутствующий сохранённый результат блокирует восстановление. Fencing предотвращает новые назначения старым владельцем, но не останавливает уже запущенную модель.

Удержанный слот снимается только после остановки прежнего вычисления. Остановите координатор и соответствующий worker, убедитесь в завершении модели, затем запустите offline maintenance в той же конфигурации и с тем же volume:

```bash
docker compose run --rm --no-deps gigaam python -m speech_receiver.main \
  --config /app/config/prod.yaml --release-held local --upstream-stopped
```

После этого запустите сервис снова. Для удалённого экземпляра вместо `local` задайте его ID. Команда отклоняется, пока volume занят действующим процессом.

## Несколько моделей

По умолчанию `instances: []` означает модель в том же процессе и один слот. Для расширения в YAML координатора задаются экземпляры того же HTTP-протокола:

```yaml
instances:
  - id: gigaam-a
    url: http://gigaam-worker-a:8000/transcribe
    token: REPLACE_WITH_PRIVATE_WORKER_SECRET
    slots: 1
    models: [v3_e2e_rnnt]
```

`models` необязателен и содержит канонические имена ASR-моделей. До выбора worker отсутствие `model` разрешается через `MODEL_NAME` координатора, а alias (например, `ctc`) — в каноническое имя (`v3_ctc`). В очередь и worker передаётся явное каноническое имя; без совместимого worker запрос отклоняется до сохранения. TTS-экземпляры одного пула должны иметь одинаковую голосовую идентичность; разные голоса требуют отдельных совместимых пулов, произвольное смешивание не поддерживается.

Удалённый экземпляр запускает существующий Python-сервис с `mode: worker`, `instances: []`, приватным токеном только для координатора. Он не создаёт дополнительную очередь: выполняет один вызов либо отвечает 429. Подтверждённые `not-started` ответы 429/503 возвращают задачу в очередь с паузой 250 мс и исходным сроком ожидания; временный отказ не кешируется как окончательный результат. Если к моменту такого отказа отключились все ожидающие клиенты, задача отменяется под блокировкой, без повторного запуска worker. Прочие окончательные ответы сохраняют состояние выполнения worker, в том числе при повторе по ключу. Освобождение worker-слота выполняется только callback завершения соответствующей задачи inference, независимо от скорости отправки HTTP-ответа. Настройте `slots: 1` для каждого такого worker. Workers не публикуются клиентам. При неопределённом транспортном сбое координатор удерживает их слот. Изменение протокола требует адаптации кода, а не только URL.

## YAML и окружения

`gigaam/config/prod.yaml` и `voxcpm2/config/prod.yaml` содержат одинаковую пару клиентов: `development` с приоритетом normal и `production` с приоритетом high. По решению владельца их постоянные токены хранятся в Git: модели доступны только в доверенной локальной сети. Эти токены задают класс клиента, а ограничение доступа обеспечивает сеть. Их значения согласованы с dev/prod-конфигурациями voice gateway AI Tutor и не меняются при перезапуске. Независимо от запуска dev/prod приёмник обслуживает оба класса в одной очереди.

Production Compose напрямую подключает эти файлы; deployment-каталог и ручное заполнение клиентских токенов не требуются. Приватные worker-токены для удалённых экземпляров в Git не добавляются. При смене клиентского токена обновляйте обе стороны согласованно.

REPLACE-токены намеренно отклоняются загрузчиком. Таймауты и retention задаются числом секунд. Обычные настройки: `brokers`, `topic`, `data_dir`, `instances`, `max_high`, `max_normal`, ограничения размеров, `queue_timeout`, `execution_timeout`, `retention`, `host`, `port`. Неизвестные поля и дубликаты отклоняются. `.env` не меняется; прежние MODEL/DEVICE/HF_TOKEN настройки моделей сохраняются.

Локально: `./dev.sh -d`. Сервер: подготовить образы, затем `./prod.sh -d`; prod использует существующий GPU override и не собирает образы при запуске. Вне доверенной сети между хостами нужен HTTPS reverse proxy. Внешний доступ должен вести только на настроенные координаторы, а не на незащищённые model-only запуски.

Приоритет строгий, без вытеснения: работающий normal завершится, следующий ожидающий high запустится перед normal. Постоянный high способен задерживать normal без верхней границы. Ограничения HTTP-допуска и ожидания раздельные по приоритету; файловая квота и доступность процесса общие.

## Бюджеты для пяти одновременных клиентов

В коммитных YAML STT настроен на 25s очереди и 5s ожидания выполнения; TTS — на 250s очереди и 60s ожидания выполнения. На один слот очередь позволяет дождаться четырёх предыдущих задач, завершающихся в пределах execution_timeout: 4×5s плюс запас для STT, 4×60s плюс запас для TTS. Таймаут ожидания не останавливает вычисление; при зависании worker арифметика не гарантирует обслуживание очереди.

В контрольном прогоне через локальный AI Tutor gateway выполнены 40 реальных запросов к прежним GigaAM/VoxCPM API. На пяти одновременных TTS-текстах по 488 символов: максимальное ожидание 141,4s, полный ответ 176,7s, отдельный HTTP-вызов до 35,4s. На пяти WAV по 25,28s: ожидание около 4s, полный ответ около 5s; одиночные STT-вызовы до 1,52s. Это проверка прежнего API через локальный gateway, а не нагрузочный прогон нового приёмника. Выборка не даёт надёжного производственного p95/p99. Для длинных STT-записей, других текстов, фонового прогрева и постоянного потока high нужны отдельные замеры; normal может не дождаться выполнения.

Согласованные значения AI Tutor: HTTP STT=40s, HTTP TTS=340s, общий gateway=370s, backend voice=400s, браузер STT/TTS=430s. Внешние ограничения включают внутренние: сроки не складываются, предыдущие этапы расходуют оставшийся бюджет. Обновите клиентские конфиги до включения принимающей очереди.

## Проверки

```bash
uv sync --project receiver --locked --group test
TEST_KAFKA_BROKERS=127.0.0.1:19092 uv run --project receiver --locked --group test python -m pytest receiver/tests -q
```

Без TEST_KAFKA_BROKERS Kafka-тесты явно пропускаются. HTTP-тесты моделей используют локальные заглушки и подключают настоящий middleware; веса/GPU не требуются. При изменении обеих сторон также проверяйте Go gateway в ai_tutor. Receiver runtime dependencies закреплены отдельным uv.lock и устанавливаются в существующий model image; версии FastAPI хост-приложения не переопределяются.


Проверка установки пакета в изолированном Python 3.12 контейнере без весов моделей:

```bash
docker build -f receiver/Dockerfile.check -t speech-receiver-check .
docker run --rm --network host -e TEST_KAFKA_BROKERS=127.0.0.1:19092 speech-receiver-check
```

Это проверочный образ, не дополнительный сервис развёртывания. Полные модельные образы используют существующие Dockerfiles; теперь их build context — корень репозитория.

Порядок включения авторизации: сначала обновить AI Tutor, чтобы он отправлял dev/prod-токены из согласованных YAML ещё в прежние модельные API; затем включить принимающую очередь. Существующие model-only API продолжают работать до включения приёмника, высокий приоритет появляется после него. Необновлённые клиенты после включения проверки токена получают 401. Неавторизованного режима совместимости нет.
