# Выбор модели и воспроизводимость

Проверено по опубликованным исходникам 27 октября 2026 года.

## Почему INT4 AutoRound

В [руководстве vLLM-Omni по AutoRound](https://github.com/vllm-project/vllm-omni/blob/9842ebc17cf1d9c6b440ecb6a79039162f68a1dd/docs/user_guide/quantization/autoround.md)
явно указан `Intel/Qwen3-Omni-30B-A3B-Instruct-int4-AutoRound` и поддержка
NVIDIA Ampere/Hopper. Формат квантования определяется конфигурацией checkpoint;
отдельный глобальный `--quantization` не нужен.

[Конфигурация модели Intel](https://huggingface.co/Intel/Qwen3-Omni-30B-A3B-Instruct-int4-AutoRound/blob/c3ef7bbf0b9d866866136c1d08b6314d27f7e151/config.json)
задаёт 4 бита, группу 128, `auto_round:auto_gptq` и область
`thinker.model.layers`; `enable_audio_output=true`.
[Индекс весов](https://huggingface.co/Intel/Qwen3-Omni-30B-A3B-Instruct-int4-AutoRound/blob/c3ef7bbf0b9d866866136c1d08b6314d27f7e151/model.safetensors.index.json)
содержит Thinker, Talker и Code2Wav; суммарный размер тензоров
26 258 064 482 байта, около 24,46 GiB. Число упакованных элементов индекса
не следует интерпретировать как число параметров исходной модели.

NVFP4 W4A4 не выбран: его документированный нативный путь для этой модели
рассчитан на Blackwell, тогда как целевые 80-ГБ A100/H100 имеют другую
архитектуру. Load-time квантование BF16 добавляет лишние требования при
загрузке. Готовый INT4 checkpoint позволяет не выполнять калибровку на сервере.
Ограничение NVFP4 приведено в
[руководстве ModelOpt](https://github.com/vllm-project/vllm-omni/blob/9842ebc17cf1d9c6b440ecb6a79039162f68a1dd/docs/user_guide/quantization/modelopt.md#qwen3-omni-nvfp4-w4a4-thinker).

## Зафиксированный runtime

Базовый образ — официальный `vllm/vllm-openai:v0.32.0`, Linux amd64 manifest
`sha256:6ee133356d49ed24cee03dd0cda3d3980279a11c107ce3e752c89e76540f41c9`.
Digest получен через Docker Registry API. Архитектура контейнера задана явно.

Omni устанавливается из коммита `9842ebc17cf1d9c6b440ecb6a79039162f68a1dd`.
Его [официальный Dockerfile](https://github.com/vllm-project/vllm-omni/blob/9842ebc17cf1d9c6b440ecb6a79039162f68a1dd/docker/Dockerfile.cuda)
использует ту же базовую версию vLLM. Мы дополнительно закрепили digest,
предотвратили замену CUDA binary stack constraints-файлом и сохраняем
`/opt/s2s/installed-packages.txt` внутри построенного образа.
После реальной сборки выявлены две особенности базового образа. Версии
OpenTelemetry согласованы на 1.40.0 с учётом требований LMCache; удалены два
неиспользуемых transport/common-пакета от другой линии OpenTelemetry,
попавших в базовый образ. Проверка зависимостей подтверждает отсутствие
ссылок оставшихся пакетов на удалённые дистрибутивы. NCCL 2.30.7 сохранён: официальный
[Dockerfile vLLM](https://github.com/vllm-project/vllm/blob/5df63a7203cdb9328d824a27b682e77c7b9928be/docker/Dockerfile#L852)
намеренно заменяет строгий pin PyTorch 2.29.7 ради DeepEPv2, которому нужен
NCCL от 2.30.4. `check_dependencies.py` проверяет все установленные зависимости
и допускает только это точное документированное исключение; остальные
несовместимости прерывают сборку.
Фактически разрешённые версии Python-зависимостей закреплены в `constraints.lock`
и используются при сборке. Omni получает версию `0.32.0+g9842ebc`, соответствующую
base runtime и source commit. Это constraints версий, а не lock с хешами всех
артефактов. Для повторного использования следует сохранить уже
проверенный образ через `docker image save` либо во внутреннем registry.

Минимальный драйвер 580.95.05 выбран для CUDA 13.0 Update 2 по
[таблице NVIDIA](https://docs.nvidia.com/cuda/archive/13.0.3/cuda-toolkit-release-notes/index.html).
Контейнерная проверка выполняет BF16 matmul и синхронизацию CUDA на реальной GPU.

## Однокарточная конфигурация

Основа — [конфиг трёх стадий Omni](https://github.com/vllm-project/vllm-omni/blob/9842ebc17cf1d9c6b440ecb6a79039162f68a1dd/vllm_omni/deploy/qwen3_omni_moe.yaml).
В нашей копии все `devices` равны `0`, доли VRAM — 0,50 + 0,15 + 0,05 = 0,70.
На карте 80 GiB это бюджеты примерно 40 / 12 / 4 GiB. Оставшиеся 30% —
плановый резерв для GigaAM/VoxCPM2 и общих накладных расходов на той же карте.
Настройка `gpu_memory_utilization` задаёт бюджет экземпляра vLLM,
но не аппаратное разделение VRAM. Это инженерное
распределение, **не опубликованный результат проверки именно этого профиля**.

Thinker использует квантование из checkpoint. Для BF16 Talker/Code2Wav
checkpoint-level quantization metadata очищены через `hf_overrides`.
CUDA graphs отключены для уменьшения сложности первого запуска. Оставлены
межстадийные чанки upstream, ограничены контекст и число активных
последовательностей, отключены неиспользуемые входы изображений/видео.
Сохранён upstream CUDA rotary custom op, указанный авторами для качества аудио.

Сервис работает с завершёнными репликами. HTTP-обёртка на порту 8002 принимает
multipart upload, ограничивает размер/длительность, нормализует аудио и допускает
только один запрос; остальные получают 429. Она имеет `/health`, `/metrics` и
OpenAPI `/docs`. `POST /chat` обращается к Thinker с `modalities: ["text"]`;
история передаётся в запросе. Слот генерации общий с голосовой ручкой.
Аутентификация, хранение истории, VAD и realtime UI — отдельная интеграция.

## Что проверяется автоматически

- До загрузки: ОС, карта, драйвер, память хоста, свободная VRAM, диски и порт.
- В контейнере: версия vLLM, CUDA, BF16 и доступ к одной GPU.
- После скачивания: pinned revision, INT4 Thinker, наличие трёх стадий,
  соответствие индекса заголовкам safetensors, полные размеры файлов и тензоров.
  Проверка структуры не заменяет криптографическую проверку всех байтов весов.
- После запуска: текст → непустой WAV → запрос с этим WAV → текст и непустой WAV.
- Локальные unit-тесты проверяют отказ на повреждённых весах, потерянной
  голосовой стадии, текстовом ответе без аудио и неправильном WAV.

Локально выполнены 39 тестов, `bash -n`, `docker compose config` и
проверка ссылок. Отдельно пройден сетевой тест в трёх Docker-контейнерах:
настоящий Uvicorn, multipart upload, ffmpeg, WAV/JSON, ошибки, docs и метрики;
upstream в этом тесте — явно выделенная заглушка, не модель.
Дополнительно через HTTP Range прочитаны реальные заголовки
всех 13 safetensors-файлов pinned checkpoint: имена тензоров совпадают с
индексом, размеры файлов и суммарный объём тензоров подтверждены. Полные
веса при этой проверке не скачивались.

## Что ещё не подтверждено

Образ собран в текущем workspace; зависимости и чтение `deploy.yaml` проверены
внутри контейнера. Запуск Qwen рядом с GigaAM/VoxCPM2 на общей GPU не проверен.
Пик VRAM, задержка, качество русской речи, устойчивость к длинной истории и
нагрузке не измерялись. Это должен установить серверный прогон, а не чтение
model card. Автотест не оценивает правильность ответа и естественность голоса.

Архитектурный разбор исходного репозитория сохранён в
[первоначальном исследовании](../docs/qwen3-omni-deployment.md).
